# DECISIONS.md — журнал решений

Правила ведения (договорились на старте, см. README):
- одно решение = один блок `D-NNN`; нумерация не переиспользуется;
- статусы: `принято`, `принято (ожидает подтверждения ...)`, `отменено (см. D-XXX)`;
- сюда пишем и **открытые вопросы**, чтобы контекст жил в репозитории, а не в чате.

---

## Принятые решения

### D-001. Репозиторий и venv — внутри `Smena/`
Принято: 2026-11-08.
Пустой `.git` и пустой `venv`, случайно созданные в родительской папке `codesss/proj`,
удалены (коммитов не было — потерь нет). `git init` и `.venv` выполнены в `Smena/`.
Ветка по умолчанию — `main`. Имя `.venv` (с точкой), чтобы не путать с будущими окружениями
и чтобы `.gitignore` его гарантированно накрывал.

### D-002. Конфигурация через переменные окружения, без pydantic-settings
Принято: 2026-11-08.
`app/config.py` читает env; для локальной разработки поддерживается файл `.env`
(простейший парсер в самом модуле, переменные окружения имеют приоритет над файлом).
На VPS источник — `Environment=` в systemd unit. pydantic-settings не вводим:
зависимости держим минимальными (в стеке ТЗ его нет). `.env` в `.gitignore`,
шаблон — `.env.example`.

### D-003. PRAGMA SQLite задаются на каждом подключении
Принято: 2026-11-08.
`journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout=5000`, `foreign_keys=ON`
устанавливаются обработчиком события `connect` (файл `app/db.py`) — иначе WAL/лимайты
не применялись бы к новым соединениям пула. `BEGIN IMMEDIATE` — helper
`immediate_transaction()`; сервисные функции на T05+ обязаны писать изменения
только через него (единственный воркер uvicorn это допускает, ТЗ требует именно так).

### D-004. Фабрика приложения `create_app(settings)`
Принято: 2026-11-08.
Нужна pytest с временной БД: каждый тест строит приложение со своими настройками.
`app = create_app()` остаётся на уровне модуля для `uvicorn app.main:app`.

### D-005. Публичные OpenAPI-схемы отключены
Принято: 2026-11-08.
`docs_url=None`, `redoc_url=None` — публичного API у продукта нет, только формы;
схема упрощала бы разведку атакующему. Для разработки схемы не нужны (маршруты читаются в коде).

### D-006. Служебный маршрут `GET /health`
Принято: 2026-11-08.
Возвращает `{"status":"ok"}` без обращения к БД; используется для проверок
живости (Caddy `request timeout 10 с`, systemd-скрипты, будущий мониторинг).
В ТЗ такого маршрута нет — это надстройка для T13/Caddy healthcheck;
публичных ссылок на него нет.

### D-007. Текст ТЗ v1.1.2 зафиксирован в репозитории
Принято: 2026-11-08.
DOCX преобразован в текст и лежит в `docs/TZ-v1.1.2-izvlechenie-teksta.txt`
(скрипт извлечения — `docs/_extract_tz.py`). Репозиторий теперь самодостаточен:
срез требований для новой задачи можно брать из файла, а не из чата. При выходе
новой версии ТЗ — обновить файл и сделать запись здесь.

### D-008. Конфигурация приведена к таблице «Конфигурация» ТЗ
Принято: 2026-11-08 (заменяет D-002 в части имён).
Имена env — ровно как в ТЗ: `SECRET_KEY` (обязателен, приложение не стартует
без него), `DATABASE_PATH` (вместо преждевременного DATABASE_URL), `TRIAL_DAYS`,
`ACCOUNT_LIMIT`, `PENDING_OVERDUE_HOURS=12`, `ISSUE_STALE_HOURS=24`,
`ISSUE_STALE_CARRIES=2`, `DEFAULT_TIMEZONE`, `BACKUP_REMOTE`.
Список поясов для регистрации — `config/timezones.txt` (по ТЗ);
тексты ошибок `messages_ru.py` — на T11 (как в ТЗ).

### D-009. Время в БД — наивный UTC (текстовое/DATE-TIME сравнимо)
Принято: 2026-11-08.
NFR-7: храним UTC, показываем в поясе отеля. Колонки — `DateTime` без tzinfo,
значения пишются `utcnow()` (naive UTC). Сравнения и сортировки в SQLite тогда
корректны; конвертация в пояс отеля — слой представления (T05+, zoneinfo).

### D-010. Схема T02: частичные индексы и CHECK вместо сервисных дублей
Принято: 2026-11-08.
«Не более одной OPEN-смены на администратора» и «один MANAGER на отель» —
частичные уникальные индексы SQLite (`WHERE status='OPEN'`, `WHERE role='MANAGER'`);
CHECK-ограничения: CLOSED⇔closed_by/closed_at, handed_at при PENDING/ACCEPTED,
receiver_id≠sender_id, обязательность receiver-полей при ACCEPTED, перечисления статусов.
Лимит 10 активных записей — ТОЛЬКО в сервисе (как в ТЗ: «проверка в сервисе»),
в схеме не отражён. Триггеры `BEFORE UPDATE/DELETE … RAISE(ABORT)` на
handover_item и issue_event создаются слушателем `after_create` — вместе со схемой.
Время: 21 автотест (создание схемы, 3 триггера-сценария, CHECK, частичные индексы, FK).

### D-011. Сессия и CSRF (T03): подписанные cookie, double-submit
Принято: 2026-11-08.
Сессии на сервере нет (ТЗ «Жизненный цикл данных»): cookie `smena_session` —
подписанный itsdangeros­-токен `{uid}`, срок 30 дней (FR-A2), флаги
HttpOnly/Secure/SameSite=Lax (NFR-2); роль/отель/активность всегда читаются из БД,
`is_active` — на каждый запрос. Flash-сообщение — отдельная подписанная одноразовая
cookie (переживает 303-редирект). CSRF — double-submit: cookie `smena_csrf`
(не HttpOnly — значение нужно в скрытом поле формы) + поле `csrf_token`,
сверка `secrets.compare_digest`; токен выдаёт middleware на каждый запрос.
Ошибки: POST 403/409 → 303 + красный flash с кодом; GET 403/404/409 → страница
ошибки (Q-002); AUTH_REQUIRED → 303 на /login без сообщения.
Важно для ручной приёмки локально: Secure-cookie браузеры принимают только по
HTTPS **или на localhost** — локальный запуск смотреть как
`http://127.0.0.1:8000`, не по IP машины. На VPS работает через Caddy HTTPS.

### D-013. Показ времени в поясе отеля и tzdata (T05)
Принято: 2026-11-08.
Хранение — naive UTC (D-009); отображение — app/times.py: zoneinfo-пояс отеля,
форматы макетов ТЗ («09:02», «01.11.2026 09:03»), возраст «1 ч 20 мин»
(часами до 48 ч, затем «3 дн»), русская плюрализация. На Windows zoneinfo не
находит IANA-базу — в requirements добавлен пакет tzdata (на Ubuntu он не
нужен, но и не мешает). Возраст вычисляется при отображении (FR-2.4/FR-3.1),
в базе не хранится (AL-5).

### D-014. Снимок пользователя для шаблонов (T08, bugfix)
Принято: 2026-11-08.
Обнаружено тестом AC-6: если сервисная транзакция сделала rollback, ORM-объект
current_user «просрочен», к моменту рендера страницы ошибки сессия закрыта и
base.html падал (DetachedInstanceError → 500 вместо 404). Решение: current_user
/ optional_user кладут в request.state.user_view плоский снимок
{role, display_name}; шаблоны верха читают только его. ORM-объект остаётся для
логики внутри обработчика. POST-ошибки NOT_FOUND в сервисе теперь несут
redirect=/journal (303+flash по контракту), GET — страница 404.

### D-021. Правки по итогам выката на Caddy 2.11 / образе TimeWeb (09.11.2026)
Статус: принято.
* `max_body` в Caddyfile — директива Caddy v1, `caddy validate` на 2.11 её
  отвергает; правильно `request_body { max_size 65536 }` — те же 64 КиБ по ТЗ.
  Caddyfile отформатирован `caddy fmt` (валидация ругалась на форматирование).
* На образе TimeWeb в ufw нет профиль-приложения «Caddy Full» (в списке только
  OpenSSH) — порты открыты явно: `ufw allow 80/tcp; ufw allow 443/tcp`;
  README-deploy дополнен.
* У VPS нет hairpin NAT на свой публичный IP: проверки §9 с самого VPS идут
  через `curl --resolve <домен>:443:127.0.0.1` (для smoke_live та же трюк —
  временная строка в /etc/hosts). Наружу с клиентской машины всё работает.

### D-022. Харднинг VPS и самопроверка памяти (09.11.2026, ночь)
Статус: реализовано.
* SSH только по ключу: PasswordAuthentication no, PermitRootLogin prohibit-password.
  Ловушка образов: sshd применяет ПЕРВОЕ встретившееся значение опции, а Include
  по алфавиту грузит 50-cloud-init.conf раньше 99-smena.conf — drop-in лежит в
  /etc/ssh/sshd_config.d/00-smena.conf; итог проверять `sshd -T`, а не файлом.
  Страховка «автооткат через 3 мин, если ключ не сработает» снята после проверки.
* systemd-лимиты smena (drop-in 50-mem.conf): MemoryHigh=300M, MemoryMax=450M
  (штатно ~75 МБ): при утечке — kill по лимиту и Restart=always, VPS не ложится.
* journald SystemMaxUse=200M; logrotate smena-backup.log weekly×8
  (обязателен `su root root` — /var/log group-writable, иначе logrotate молча
  пропускает ротацию).
* OOM-диагностика по жалобе пользователя: на VPS за все загрузки НОЛЬ oom-kill,
  свободно ~1.5 ГиБ — прод ни при чём. (Первая гипотеза «нехватка RAM на клиентской
  машине» позже опровергнана скриншотом: CUDA OOM на инференс-сервере модели,
  31 ГиБ GPU — к проекту отношения не имеет, см. D-023.)

### D-023. Автопробежка AC-пунктов на проде и мобильная починка (09.11.2026, утро)
Статус: реализовано.
* AC-10 вживую на проде: POST /issues при read-only файле БД (chmod 444 +
  каталог 555 + restart) → 500 «Запись не сохранена», форма сохранила введённые
  значения, integrity_check ok, после возврата прав запись проходит. Важный
  побочный факт: без открытой смены POST уходит в 303+NO_OPEN_SHIFT и до записи
  не доходит — тест сначала должен открыть смену.
* Уборка за тестом вскрыла особенность схемы: триггеры immutable (issue_event,
  handover_item) блокируют и DELETE — прямая чистка «по-админски» требует
  временного DROP TRIGGER (сделано в транзакции, триггер восстановлен).
* AC-13 (безопасность) на проде: argon2id во всех password_hash; Set-Cookie
  smena_session HttpOnly+Secure+SameSite=Lax; POST без CSRF → 403 «Страница
  устарела…»; http→https — Caddy отдаёт 308 (не 301, строже и корректнее для
  POST — в чек-листе уточнено).
* AC-13 (мобильный) — автопрогон headless-Edge 360×800 по всем 12 экранам
  (puppeteer-core + системный Edge; playwright/pypi из этой сети недоступен):
  горизонтальный скролл 0; попутно исправлено в app.css: .linklike («Выйти»),
  .tab (вкладки истории) и поля фильтров истории были <44 px — подняты до
  NFR-6. Скриншоты и measure.json — в docs/accept/ (не коммитятся, см. шапку
  чек-листа; в git — только чек-лист с отметками).
* Проверка NFR-1 (10 одновременных, 200 запросов с самого VPS): p50 59 мс,
  p95 189 мс, p99 323 мс, max 349 мс — запас двукратный до 2 с.
* Инференс-сервер модели (deepcode.ci.nsu.ru, 31 ГиБ GPU) падал с CUDA OOM из-за
  раздутого контекста чата; обе модели отвечают, автоhealth-check каждые 2 ч
  поставлен в планировщике сессии.

### D-024. scripts/live_acceptance.py — живой AC-прогон одним скриптом (09.11.2026, ночь)
Статус: реализовано; 38/38 PASS локально и на одноразовом VPS-стенде.
* `scripts/live_acceptance.py <БАЗА>` прогоняет AC-1…AC-8, AC-11 и путь AC-12
  по HTTP против РАЗВЁРНУТОГО приложения на новых тестовых отелях (slug по
  времени) — seed-данные и прод не затрагиваются. Выход 1 при любом провале,
  в конце — счётчик PASS/FAIL и SLUG тестовых отелей.
* Переносной HTTP-клиент (не httpx- редиректы!) оказался сутью задачи: наш CSRF
  после успешного POST выдаёт `smena_csrf=""` (удаление), а middleware ставит
  НОВЫЙ токен на следующем ответе. Браузер (и наш клиент) обязан: снимать
  кавычки с значения cookie, пустое значение считать удалением и обновлять jar
  ПЕРЕД каждым переходом 303. httpx с follow_redirects это ломал (403
  CSRF_FAILED на каждом POST) — редиректы идут вручную.
  Для будущих скриптов: не настраивать «свой cookiejar» поверх httpx-редиректов.
* Ловушки проверок (по факту приложения, не по памяти чек-листа): вопрос
  закрытой смены для автора — ISSUE_CLOSED, а не SHIFT_NOT_EDITABLE; без
  открытой смены POST отдаёт NO_OPEN_SHIFT раньше проверки принадлежности —
